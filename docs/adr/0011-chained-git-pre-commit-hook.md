# 11. The global pre-commit hook chains to the project's own

Status: Accepted

Files: `modules/home/git.nix`

Supersedes the mechanism in ADR 0004; the reason for scanning globally is
unchanged.

## The problem

`core.hooksPath` does not add a hooks directory, it replaces `.git/hooks`
entirely. Git resolves hooks from exactly one place. So a global
`core.hooksPath` carrying a gitleaks `pre-commit` silently disables every
project-installed hook on the machine: `simple-git-hooks`, `lefthook
install`, and `pre-commit install` all write real files into `.git/hooks/`,
and git stops looking there.

Silently is the operative word. There is no warning, no non-zero exit; the
team's lint simply never runs, and the failure surfaces later as a CI
rejection nobody can reproduce locally.

`programs.git.hooks.pre-commit` (home-manager) is a thin wrapper over exactly
this, which is why it was dropped in favour of writing the hook and
`core.hooksPath` by hand.

## The fix

One dispatcher script installed at `~/.config/git/hooks/pre-commit`, with
`core.hooksPath` pointed at that directory. It runs gitleaks, then hands off
to the project's hook with `exec`, forwarding arguments and stdin.

`set -eu` gives the ordering guarantee that matters: gitleaks runs first and
a leak aborts the commit before the project hook is ever reached, so a secret
can't slip through on the back of a lint failure being fixed.

Locating the project hook has two traps. `git rev-parse --git-path
hooks/pre-commit` honours `core.hooksPath`, so it returns the dispatcher's
own path and would loop. And `--git-dir` is wrong in a linked worktree: it
resolves to `.git/worktrees/<name>`, which has no `hooks/` directory, so the
project's hook would be silently skipped there, which is the same failure
this whole change exists to remove. Hooks live in the shared directory, so
the dispatcher uses `$(git rev-parse --git-common-dir)/hooks/pre-commit`.

That call cannot be replaced with `''${GIT_DIR:-.git}` to save the process
spawn. Git exports `GIT_DIR` per worktree and does not export
`GIT_COMMON_DIR` at all, so parameter expansion cannot reach the shared
directory. The spawn costs about 4ms per commit and buys worktree
correctness.

`~/.config/git/hooks` is used rather than the store path home-manager would
otherwise generate, because the path has to stay stable across rebuilds for
the per-repo escape hatch below to keep working.

## Checks are data, not script text

`globalChecks` is a list of `{ package; args; }`, rendered into the script by
`runChecks`. Adding a global check is one list entry; the script body never
changes, and `lib.escapeShellArgs` handles quoting. The generated file is
still a shell script, because a git hook has to be an executable, but what
runs in it is configuration rather than prose.

Promoting this to a `lib.mkOption` that other modules contribute to (the way
`modules/work.nix` additively contributes to `home.packages`) buys nothing
today: one check, one consumer. Do it the day a second module needs to add
one.

## Only `pre-commit`

Every other hook type (`commit-msg`, `pre-push`, ...) stays uncovered, and a
project that installs one gets the silent breakage described above. That is a
deliberate trade: nothing here uses them today, and installing a dispatcher
under all fifteen client-side hook names would spawn a shell on every
checkout, merge, and rebase for hooks that do not exist. The symptom to
recognise is "the team's hook just doesn't run".

Adding a second hook name is not free, and the code should be changed rather
than copied. `hookName` is bound once so the dispatcher has no hardcoded name
in its body, but a second name still needs `preCommit` turned into a function
of the name and `xdg.configFile` generated by mapping over a list. Copying
the binding instead would duplicate the `--git-common-dir` and husky
handling above, and the two copies would drift silently.

## The husky case, which this does not solve

A repo-local `core.hooksPath` outranks the global one. `husky` sets exactly
that (`.husky/_`) during `npm install`, which means husky repos capture hook
dispatch entirely and gitleaks stops running there, with no warning. No
global config can prevent this; git reads one hooksPath and local wins.

The recovery is per-repo and manual:

```sh
git config --local core.hooksPath ~/.config/git/hooks
```

That hands dispatch back, and the `.husky/_/pre-commit` candidate in the
dispatcher's search order is what keeps husky's own hooks working afterward.
That candidate is unreachable under normal husky operation and exists solely
to make this escape hatch viable.

Do not apply that recovery in a `simple-git-hooks` repo. `simple-git-hooks`
reads `git config --local core.hooksPath` (local only, never global) and
installs its hook *into* that directory, so pointing it at the read-only
`~/.config/git/hooks` symlink makes `pnpm install` fail with `EACCES`.
Leaving the local setting unset is what keeps it writing to `.git/hooks/`,
where the dispatcher expects to find it.
